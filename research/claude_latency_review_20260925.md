# Claude 설명 검증 — 지연, 회피 가능성, 브라우저 제어

기준일: 2026-09-25. 코드·저장된 P18/P18b 기록·로컬 재계산에 근거한 검토 의견이다. 새 알고리즘 구현이나 실사이트 실행 승인이 아니다. 운영 코드를 수정하거나 실행 중인 시험을 시작·중단하지 않았다.

## 결론

브라우저 안에서 제어하고 상대의 미래 기동을 고려하자는 방향은 타당하다. 그러나 **현재 설명만으로 ‘실제 지연 60~90ms’, ‘50px에서는 물리적으로 회피 불가능’, ‘수십 ms를 줄여도 결과가 거의 같다’를 확정할 수 없다.** 지연 추정의 의미와 회피 기하 계산을 먼저 바로잡아야 한다.

현재 P18에는 이전 Codex 리뷰의 최종 명령 검사·코일 예측 관련 수정이 반영돼 있다. 과거 버전의 결함을 이번 버전의 미수정 결함으로 반복하지 않는다. 다만 수정 반영과 실전 성능 검증 완료는 다르다.

검토한 SHA-256:

- `pilot.py`: `ddffaf1dc2a8f6a561d04e15cb477fddcee3f26a4c2192a5c638850bddf93920`
- `run_live.py`: `8110ad7bbfc88aef2c0cf28e2ea7d6d8ea30371ef5050146100317c5b551b423`
- 보관 클라이언트 `research/game.js`: `5ad8aa8f06d1e71bad2945001bab077f8d4d279c093a046d19b6f26ac6b62095`

## 1. 60~90ms는 재현되지만 명령 적용 지연의 직접 측정값은 아니다

원래 코드와 같은 방향 일치율 분석을 읽을 수 있는 P18 8판에 적용했다. 각 판의 마지막 900개 관측이다. `live_20260925_173418`은 EOFError로 읽지 못해 제외했으며 원인은 확정하지 않았다.

| 관측 시각에 더한 지연 | 방향 일치율 평균 |
|---|---:|
| 0ms | 86.53% |
| 30ms | 91.49% |
| 60ms | 94.02% |
| 90ms | 94.24% |
| 120ms | 90.13% |

개별 최고점은 6판에서 90ms, 2판에서 60ms다. 따라서 계산 결과 자체가 조작되거나 전혀 재현되지 않는 것은 아니다. **그 결과를 해석한 방식이 문제다.**

- `run_live.py:136–151`: 상태 `t`는 관측 요청 전 루프 시작 시각이다. 명령은 관측·판단·블랙박스 기록 후 페이지에 전달한다. 실제 명령 기록 시각과 다르다.
- 비교 대상은 시점 하나의 반응 시작이 아니라 `t+L`부터 `t+L+60ms`까지 각도 변화의 부호다.
- 같은 방향의 명령과 회전은 여러 틱 지속된다. 이미 돌던 움직임도 일치로 집계된다. 지연 0에서도 86.53%가 맞는다.
- 일정하게 회전하며 그 앞을 향하도록 명령하는 합성 자료에서는 모든 지연의 일치율이 100%다. 이 방법만으로 지연을 식별할 수 없는 경우가 있다.
- 관측된 클라이언트 각도 변화는 서버가 해당 명령을 적용한 순간의 확인 메시지가 아니다.

정확한 표현은 **‘현재 관측·명령 기록의 방향 일치가 60~90ms 오프셋에서 높았다’**다. 이를 서버 지연이나 실제 입력 반응 시작 시간으로 단정하거나, 관측→명령 중앙값을 빼서 나머지를 줄일 수 없는 서버 지연이라고 분해할 수 없다.

같은 8판의 저장된 `stage_ms.obs_to_cmd`도 다시 확인했다.

- 판별 p50 범위: **33.7~46.5ms**; 8개 p50의 중앙값 36.55ms.
- 판별 p95 범위: **54.6~102.0ms**.
- 판별 루프 p50: 35.1~48.0ms. 초당 27회는 일부 상황의 근사치다.

이는 판별 분위수 범위이며 전체 틱을 합친 분위수는 아니다. ‘드물게 200ms’는 이번 요약 지표만으로 검증하지 못했다.

## 2. 90° 회전 시간과 직진 충돌 시간을 비교하면 회피 가능성을 오판한다

회피 중에는 방향과 위치가 동시에 변한다. 장애물이 유한한 몸체라면 90°를 완성하기 전에 옆으로 벗어날 수도 있다. 거리 50px가 머리 중심 간 거리인지, 몸체까지 거리인지, 반경을 뺀 여유인지도 구분해야 한다. 상대가 움직이면 상대 속도와 진행 방향까지 필요하다.

반례용 단순 모델: 정지한 무한 직선 벽이 정면에 있고, 속도 `v`, 최대 각속도 `ω`, 반응 지연 `τ`가 일정하다. 몸 반경을 이미 뺀 정면 여유를 `g`라고 하자. 지연 동안 직진한 뒤 최대 회전하면, 벽 쪽 최대 이동량은 다음과 같다.

`필요 여유 = v × τ + v / ω`

현재 플래너의 작은 개체 가정 `v=180px/s`, `ω=230°/s`를 쓰면 회전 반경은 44.84px다.

| 반응 지연 | 필요한 여유 | 현재 여유 60px일 때 |
|---|---:|---|
| 100ms | 62.84px | 충돌 |
| 70ms | 57.44px | 회피 |

**30ms 차이만으로 같은 모델에서 충돌 여부가 바뀐다.** 따라서 ‘수십 ms를 줄여도 결과가 거의 같다’는 결론은 나오지 않는다.

이것은 분석상의 일반화에 대한 반례다. 특정 실전 사망을 살릴 수 있다고 입증한 결과나 검증된 서버 물리 상수가 아니다. 움직이는 몸, 양쪽 장애물, 가속, 회전 오차를 포함한 실전 회피 가능성은 별도로 검증해야 한다.

30ms 동안 순항 180px/s에서 5.4px, 부스트 434px/s에서 13.02px를 이동한다는 산술은 맞다. **그 몇 px가 정밀 통과에서는 결정적일 수 있다.** 예측으로 얻는 시간과 입력 지연 감소를 단순히 50배 비교해 성능 기여를 판단할 수 없다.

## 3. 현재 코드와 사망 설명도 일부 다르다

`pilot.py:178–190`은 직진/현재 측정된 회전 각각에 현재 속도/기습 부스트를 적용한다. 회전이 충분히 측정되면 4개, 아니면 2개 경로다. **현재 회전하면서 부스트하는 경로는 이미 있다.** 빠진 것은 앞으로 상대가 새로 선택할 수 있는 회전 변화다.

`pilot.py:459–461,596–602`에는 안전 후보를 먼저 거른 뒤 그 안에서 점수를 비교하는 구조도 이미 있다. 모델이 위험을 누락하거나 안전 조건을 완화하는 문제는 남을 수 있지만, 현 구조를 ‘먹이와 생존을 점수 하나로만 섞었다’고 설명하면 부정확하다.

대화 직전의 짧은 P18b 세 판도 확인했다. 마지막 관측을 기준으로 한 수치이며 서버 사망 순간과 동일하지 않다.

| 판 | 마지막 연속 emergency 길이 | 그보다 이전의 기록 |
|---|---:|---|
| `183803` | 약 0.181초 | 1초 전에도 emergency, threat=0.69 |
| `183834` | 약 0.256초 | 0.5초 전 evade, threat=0.29 |
| `183915` | 약 0.116초 | 2초 전 evade, threat=0.71 |

따라서 마지막 emergency 구간을 최초 위험 인지 시점으로 읽어 ‘모두 0.4초 전에야 알아챘다’고 하면 안 된다. 위험 인지, 회피 선택, 안전 후보 소진, 마지막 비상 모드 진입은 서로 다른 사건이다.

마지막 가장 가까운 몸체의 소유자를 추적했을 때, `183803`과 `183915`의 해당 머리는 2초 전 표본에서 `sp≈5.79`, `183834`는 `sp=14`였다. ‘세 판 모두 상대가 부스트로 달려들었다’는 설명도 이 표본으로 확정되지 않는다. 다만 가장 가까운 몸의 소유자를 실제 가해자로 확정한 것은 아니므로 이를 완결된 사망 원인 분류로 쓰지 않는다.

## 4. JavaScript 전환은 검토할 가치가 있다. 효과 수치는 먼저 측정해야 한다

페이지 안에서 최신 상태를 읽고 최종 명령을 결정하면 Python 왕복·상태 직렬화·스케줄링 비용을 줄일 가능성이 있다. 이미 방향 전송 빈도가 제한돼 있어도 전송 직전 더 최신 상태를 사용하거나 전송 기회를 놓치지 않는 이점이 있을 수 있다.

보관 클라이언트에는 방향 전송 조건 `ctm-last_e_mtm>33`, 부스트 변경 조건 `ctm-last_accel_mtm>50`이 있다. 이는 보관본 코드의 조건 확인이며 현재 서버의 실제 처리 주기 측정이 아니다. 이 조건만으로 Python 관측 지연을 줄일 가치가 없다고 결론 내릴 수 없다.

반면 다음은 측정 전 기대치다.

- JavaScript 판단이 반드시 5ms가 된다는 주장.
- `requestAnimationFrame`이 항상 초당 60회 실행된다는 주장.
- 200ms 지연이 모두 제거된다는 주장.
- 나머지 지연은 전부 서버 몫이어서 줄일 수 없다는 주장.

[MDN requestAnimationFrame](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame)은 호출 빈도가 일반적으로 화면 갱신률을 따르며 백그라운드에서 중단될 수 있다고 설명한다. [MDN 실행 모델](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Execution_model)의 run-to-completion 특성상 페이지의 긴 작업도 후속 작업을 지연시킬 수 있다. 원문 HTML 두 개를 작업 폴더에 보관하고 workspace read_source로 해당 본문을 확인했다.

## 5. 권고하는 설계 순서 — 미채택 제안

1. **시각과 명령 이력을 일치시킨다.** 페이지의 동일한 시간 기준으로 상태 취득, 계산 완료, 최종 입력 기록, 정상 게임 전송, 첫 관측 반응을 구분해 기록한다. 명령 ID도 연결한다. 서버 적용 시각은 직접 알 수 없으면 미확인으로 둔다.
2. **최종 명령 작성자를 하나로 둔다.** Python이 목표/계획을 제공하고 페이지 제어기가 최종 경로 검사·선택·명령 기록을 맡는다. Python과 JavaScript가 각각 입력을 덮어쓰는 구조는 피한다. 실제 실행 명령을 Python에도 돌려준다.
3. **회피는 실행 가능한 기동으로 비교한다.** 좌/우 회전, 회전 후 직진, 순항/부스트 전환을 같은 물리·지연 모델로 전개한다. 근거리에는 촘촘한 검사, 먼 미래에는 불확실성을 명시한 검사를 쓴다. 명확한 몸체 충돌 제약과 불확실한 머리 위험을 구분하고 통과한 후보에서 먹이·혼잡 목표를 고른다.
4. **상대의 새 회전을 고려하되 과도하게 막지 않는다.** 긴 시간 동안 가능한 모든 머리 위치를 합쳐 영구 장애물로 두면 혼잡 지역 대부분이 막힌다. 시각별 머리 점유와 이미 생긴 몸체를 구분한다. 0.3초 여유도 검증할 매개변수다. 단순한 부채꼴이나 출구 방향 수만으로 실제 후속 경로의 실행 가능성을 보장하지 않는다.
5. **로컬에서 지연과 정책 효과를 분리한다.** 고정된 기록 상태로 계산 시간 p50/p95/p99와 최악 지연을 측정하고, 반응형 시뮬레이터에서 지연 조건을 바꿔 충돌·회피·좁은 길 통과를 비교한다. 같은 정책의 Python/페이지 구현 비교와 새 정책의 효과 비교를 분리한다.

0.5초짜리 별도 비상 덮어쓰기만 추가하면 짧은 예측과 명령 충돌 문제가 남을 수 있다. 안전 우선순위만 세운다고 방향 진동과 맴돌기가 자동으로 사라지지도 않는다. 계획 유지 조건과 재계획 조건을 명시해야 한다.

블랙박스의 미래 상대 궤적을 고정한 재생은 **그 궤적을 가정했을 때의 회피 가능성**을 확인하는 데 유용하다. 우리 행동 변경에 상대가 반응하는 실전까지 보장하거나 가능한 모든 기동을 검증했다고 말할 수 없다.

## 검증 범위와 미확인

검증: 현재 코드 정적 확인, P18 8판의 원래 방향 일치율 재계산, 판별 시간 요약, P18b 3판의 일부 관측, 단순 모델 반례, MDN 원문.

미확인: 실제 서버 명령 적용 시각, 각 사망의 정확한 가해자와 물리적 회피 불가능 시점, JavaScript 제어의 실제 계산 시간과 생존 효과, 200ms 지연의 원인, Codex 호출 취소의 원인. ‘취소됨’만으로 실행 시간 제한이나 요청 크기가 원인이라고 확정할 수 없다.

자동 검색의 `coverageStatus=missing`, `missingScopes=[KR]`는 법률 관할이 섞인 후보 검색 결과이며 기술 검증 완료를 뜻하지 않는다. 이번 결론은 로컬 원자료와 별도로 보관·읽은 기술 문서에 한정한다.
