# 실시간 제어 기술 검토 — 병목은 통신이 아니라 계산, 결과 동일 최적화로 약 40% 단축

사용자(2026-09-24): “우선은 가장 빠르게 기술적으로 테스트와 검토를 하고 말하는게 낫지 않나? 거의 리얼타임, 브라우저간 통신도 거의 리얼타임으로 → 안되면 다른 솔루션(windows에서 직접 제어 등)” / 화면 축소는 OK.

측정(bench_e2e.py: Windows Chrome에 붐비는 가짜 게임 상태 — 큰 지렁이 7마리가 주변을 감싼 장면, 적 몸 조각 3710개, 관측 105KB — 게임 서버 접속 없음):
- 관측 전송 p50 12–13ms·p95 20–22ms, 명령 4–7ms. WSL↔Windows 중계는 병목 아님 → Windows 직접 제어 이전 불필요.
- 판단 계산이 병목: 최적화 전 p50 146–165ms·p95 255–350ms·최대 520–605ms(실전 pocket5 사망 직전 0.2–0.6초 판단 간격과 일치).
- 원인(프로파일): 모든 경로 점×모든 적 몸 원 전수 거리(pocket.clearance, staged 경로 검사), 긴급 회피 순위 contact_times의 전체 쌍 행렬, 포위 판정 광선이 사거리 밖 원까지 계산.

조치(모두 결과 동일 최적화): geometry.nearest_gap(k-d 트리 최근접, 경계 미충족 점만 전수 재계산), staged 경로 검사·pocket.clearance 적용, contact_times 후보 쌍 k-d 트리 탐색(상한 기반 상위집합, 반경별 4그룹), 포위 광선은 650px 사거리 안 원만. pocket5·pocket·coil·predict 시뮬레이터 판단 기록과 붐비는 장면 contact_times 출력이 변경 전과 바이트 단위 동일. 테스트 48개·자체 검사 4종 통과.

결과(같은 가짜 장면): 전체 주기 p50 185→115ms, p95 381→207ms, 최대 547→274ms. 빠른 경로(회피·먹이·긴급 회피)만 62ms, 포위 판정 67ms(0.25초마다), 나머지는 원 경로 탐색.

남은 한계: 극단적 혼잡에서 목표(33–50ms) 미달. 다음 후보: 포위 판정·원 경로 탐색을 별도 프로세스로 병렬화(예상 주기 ≈ 80ms 극단 혼잡, 평상시 30–40ms), 제어 주기 15→30Hz, 창 960×600. 실사이트 효과는 미검증. 가짜 장면은 실제 실사이트 관측이 아니다.
