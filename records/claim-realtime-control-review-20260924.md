# 실시간 제어·작은 화면 검토 (의견 요청, 코드 변경 없음)

사용자: “우선은 좀더 빠르게 연산과 조작을 할수 있는지 확인해봐.. 거의 realtime으로.. 내가 보기에는 충분하게 피할수 있었는데, 죽더라. 그리고 캡춰할때 크기를 줄이는데, 아예 테스트화면을 줄인 상태로 진행하면 안되나? 꼭 100% 일 필요는 없음.. 우선 의견을 먼저줘”

확인한 것:
- 게임 클라이언트(research/game.js, 2026-09-23 저장본): 방향은 마지막 전송 뒤 33ms가 지나야 다시 보냄(want_e && ctm-last_e_mtm>33), 각도는 251단계(약 1.4°)로 양자화. 서버로 가는 조작의 최대 빈도는 약 30Hz. 현재 제어 주기 66.7ms(15Hz)는 그 절반.
- 화면 확대율 gsc는 뱀 길이(sct)로만 정해짐(dgsc=.64285+.514/max(1,(sct+16)/36)). 창 크기는 확대율이 아니라 보이는 영역을 바꿈. 제어기는 화면 픽셀이 아니라 게임 JS 상태를 읽음. 창 크기가 서버가 보내는 주변 데이터 범위에 영향을 주는지는 미확인.
- 로컬 판단 시간(pocket5, 시뮬레이터 2판, 모드별): 포위인데 회전 경로 없음(no_loop) p95 137ms·최대 143ms, 긴급 회피 p95 32ms, 먹이 수집 p95 24ms. 위험 구간에서 계산이 가장 무겁다.
- 실사이트 pocket5 사망 직전 판단 간격 0.2~0.6초(runs/live_staged_20260924_151819.jsonl). 관측 전송·판단 계산·스크린샷 대기 각각의 몫은 기록이 없어 미확인.

의견(미확정): (1) 판단 간격을 관측·계산·명령 단계별로 기록해 원인 확정, (2) 위험 모드는 빠른 판단을 먼저 내고 무거운 탐색은 남는 시간에만(시간 한도), (3) 제어 주기 15Hz→30Hz(클라이언트 상한), (4) 필요시 Windows용 Python으로 옮겨 중계 제거. 창 축소는 제어 속도 효과는 작고 스크린샷 비용 감소에 유효, 서버 데이터 범위 영향은 1판으로 확인 필요.
